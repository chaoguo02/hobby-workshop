# 兴趣工作坊预约订单状态机

## 状态

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| 1 | 待支付 | 支付、用户取消、超时关单 |
| 2 | 已支付 / 待核销 | 工作人员核销 |
| 3 | 已核销 | 终态 |
| 4 | 已取消 | 终态；库存和抢购资格已释放 |
| 5 | 退款中 | 预留 |
| 6 | 已退款 | 预留 |
| 7 | 关闭处理中 | MySQL 已关单并回补，等待 Redis 幂等补偿 |

主链路：

    抢券准入 -> Kafka 落库 -> 待支付(1) -> 支付成功(2) -> 到店核销(3)
                                      \-> 关闭处理中(7) -> 已取消(4)

## 并发与一致性约束

1. 支付和关单都以 WHERE id=? AND status=1 更新，二者并发时只有一个成功。
2. 关单的 1 -> 7 与 MySQL 秒杀库存 +1 在同一事务内提交。
3. 事务提交后执行 Redis Lua，一次性完成库存 +1、移除一人一单成员、删除准入记录。
4. Lua 以订单号记录补偿结果；重复执行不会重复加库存。
5. Redis 补偿失败时保留状态 7，定时任务重试；补偿完成后才更新为状态 4。
6. 取消后再次抢券可能触发数据库唯一键，订单落库逻辑需要复用已取消记录并替换为新订单号。
7. 支付是项目内模拟确认，不发生真实扣款；但仍按真实订单语义处理幂等、超时和并发。

## 用户视角的边界情况

| 场景 | 系统裁决 | 用户看到的结果 |
| --- | --- | --- |
| 支付与关单同时发生，支付先更新 | 支付获得 `status=1` 的更新权，进入状态 2 | 支付成功并生成核销码；关单跳过 |
| 支付与关单同时发生，关单先更新 | 关单获得更新权，进入状态 7 | 提示订单已关闭、本次支付未生效 |
| 用户重复点击支付 | 第一次完成状态迁移，后续请求读取数据库终态 | 均按支付成功展示，不重复处理 |
| 支付请求超时或前端断网 | 前端不猜测成功或失败，重新查询订单 | 以数据库中的状态 2、4 或 7 为准 |
| 抢券成功但订单仍在异步落库 | 本地暂存订单号并轮询本人订单 | 先显示“创建中”，落库后自动变为“待支付” |
| 倒计时归零 | 禁止继续提交支付并轮询关单结果 | 自动变为“关闭处理中”或“已取消” |

## 超时策略

- 默认支付时限为 15 分钟，可通过 WORKSHOP_PAYMENT_TIMEOUT_SECONDS 调整。
- 每 5 秒扫描一批超时待支付订单，多实例重复扫描由条件更新保证安全。
- 每 5 秒重试状态 7 的 Redis 补偿。
